# LinkTool for Claude Code 开源：把 GIS 分析、出图和报告连成一套工作流

“根据这些地块和土壤数据，做一份耕地质量评价，最后给我地图和报告。”

需求只有一句话，落到 GIS 软件里，却要先认清数据、核对坐标系和字段，再确定评价方法、组织空间计算，最后整理统计表、专题图和文字说明。每一步都有工具，费工夫的是把这些步骤接起来，并说清楚结果从哪里来。

LinkTool-ClaudeCode 是一款面向 Claude Code 的通用 GIS 分析插件，将空间分析、专题制图和报告生成接入同一套工作流。用户用自然语言描述目标，由任务规划 Agent 组织步骤，通过 MCP 调用 QGIS、GDAL、WhiteboxTools 及内置 Python 工具完成空间处理，再由可视化和报告 Agent 继续制作成果。从道路邻近分析到多因子评价，用户都可以在同一套插件中提出需求，获得分析数据、专题地图和报告。

## 01 背景：让业务需求更容易变成 GIS 成果

### 工期紧、人手少，专业分析还有不少重复工作

从一个业务目标到一份空间分析成果，往往要经过很长的操作流程。做耕地质量评价，需要整理地块与土壤数据、核对评价指标，再完成计算、分级和面积统计；分析设施服务范围，要确定距离口径、处理空间关系，还要把结果绘成地图、写进报告。业务人员知道想解决什么问题，具体用哪些工具、参数怎样设置、先后顺序如何安排，则依赖 GIS 专业经验。

初学者容易卡在软件操作和流程调试上，专业人员也要反复处理数据转换、字段核对与成果排版。在测绘、自然资源和农业农村项目中，工期和交付要求不会因为这些重复工作而放宽。一套分析方法即使已经成熟，换一批数据、换一个研究区，仍要花时间重新组织执行。

### 用自然语言提问之后，谁来把流程接起来？

用自然语言调用 GIS 工具，解决了分析入口的问题。到了项目现场，还要看一套方案能否适应不同业务，以及能把任务推进到哪一步。围绕固定场景设计的流程，换一个问题就可能需要重新搭建；只完成工具调用或返回结果图层，后续制图、统计说明与报告编写仍要由用户衔接。

如果这些衔接仍由用户完成，使用者就需要同时懂业务、懂 GIS，还要知道怎样把要求写成模型容易执行的提示词。对非专业人员而言，困难常常从打开软件、寻找菜单，转移到了组织问题和判断结果上。

我们把 LinkTool 的重点放在两件事上：让同一套插件能够组织不同类型的 GIS 分析，并把计算结果继续做成地图和报告。用户可以围绕业务目标完成任务，减少为不同场景切换工具、重写提示词和手工整理成果的工作。

### 简单描述需求，规划、分析与成果制作接着完成

LinkTool 以 task-plan Agent 作为任务规划与调度的核心，将用户的简单描述整理为目标明确、步骤清楚的结构化任务。它结合已有数据补充执行条件，安排每一步的输入、输出和验收要求，再按任务复杂度直接委派专门的 Agent，或通过 Workflow 组织执行，由 MCP 接入实际 GIS 工具。

例如，用户提出“根据这些地块和土壤数据，做一份耕地质量评价，输出地图和报告”，规划 Agent 会先查看评价单元与土壤属性，核对所需因子和评价依据。需要补充的资料、需要确认的权重与分级口径，会在执行前明确；随后组织指标处理、评价计算、分级统计和成果制作。用户无需先把整套分析流程写成一份复杂提示词。

### 一套插件，适配不同类型的 GIS 任务

**LinkTool 的通用性，体现在可以根据问题重新组织分析流程。** 道路邻近分析需要缓冲、叠加和面积统计；设施选址需要空间筛选与条件约束；多因子评价则涉及指标处理、综合计算与分级。这些任务可以由同一套规划机制组织，通过组合工具与工作流完成。

内置 Workflow 提供常用流程，task-plan 也能根据具体需求生成执行计划。换一个研究区或业务目标时，插件围绕新的数据和条件安排步骤，团队积累的方法则通过 Skill 和工作流继续复用。通用的任务组织能力与可扩展的专业方法结合，让插件的用途从单项操作延伸到完整业务分析。

### 专题地图和报告，随分析流程一起完成

**LinkTool 将分析数据、专题地图和报告作为相互对应的一套成果来组织。** 制图与报告生成已经纳入工作流，用户在提出分析需求时，就可以同时约定需要哪些图件、统计表和说明文档。

出图时，可视化 Agent 根据分析主题组织图层，选择表达字段、符号与配色，通过制图服务制作专题地图。报告 Agent 则读取执行计划、工具日志和实际结果，交代数据来源、分析方法与操作过程，并将统计结果、图件和结论整理为 Markdown 文档。过程报告方便技术人员复查，评价报告帮助业务人员理解结果。

例如，做道路邻近分析，交付内容可以同时包括范围图层、专题地图，以及说明距离口径、面积统计和处理步骤的报告。专业人员少做一轮导出、拼图和文字整理，业务使用者也能直接从图与报告中了解空间分布、结果规模及其依据。通用分析加上成套的成果表达，是 LinkTool 面向实际项目的主要优势。

## 02 项目结构：从一句需求到一份可复核的成果

### LinkTool开发过程遇到的问题及解决方案

要把 GIS 智能体用于实际项目，需要考虑工具执行前后的整段流程：如何保护输入数据，怎样检查结果，又如何把分析过程交代清楚。围绕这些要求，我们在 LinkTool 中安排了以下设计。

**操作缺少边界和记录，结果就难以复查。** 一次分析可能涉及多个图层和中间文件，模型一旦写错路径，原始数据就可能受到影响；没有调用记录，事后也很难还原用了哪个工具、哪些参数。为此，LinkTool 通过 Hook 在调用前检查文件路径、GIS 参数和输出位置，对原始数据区设置只读保护，并为需要的操作接入备份处理。调用后，工具名、参数、输入输出路径和时间写入结构化日志。遇到异常可以沿记录排查，项目复核也有了具体依据。

**得到分析数据后，往往还有出图和报告要做。** 一个结果图层并不能直接说明分析方法，也未必方便业务人员阅读。我们将成果制作交给可视化 Agent 和 report Agent 协作完成：前者组织图层、符号和配色，后者读取执行计划、日志与实际结果，整理过程说明和统计结论。计算结果由此继续转化为专题图和报告，减少人工导出、复制、排版与核对的工作。

**模型临时编写处理代码，会让执行过程难以统一管理。** 同一类操作可能采用不同的库和写法，参数检查、日志记录与错误处理也容易各行其是。LinkTool 为 gis-tool Agent 设置了明确的职责和工具约束，要求空间处理通过 MCP 调用 GIS 工具，将参数确认、执行、核查和重试接在同一条流程中。这样，每一步空间操作都有明确的输入输出，后续检查和报告引用也有统一入口。

**多步骤任务还需要管理依赖，并检查最终目标。** 例如，缓冲区生成成功后，仍要完成耕地叠加与面积统计，才能回答“道路周边有多少耕地”。LinkTool 用 Workflow 保存执行计划和步骤关系，在子任务中写明验收要求，再通过单步核验与独立的整体验证检查成果。出现失败时，规划 Agent 根据记录修复执行脚本并续跑，减少遗漏步骤或重复处理已完成任务的情况。

这些问题决定了 LinkTool-ClaudeCode 的整体分工：Agent 承担不同任务，Workflow 组织执行，Skill 提供专业方法，Hook 负责过程检查，MCP 连接实际工具。任务规划将不同业务需求接入分析流程，制图和报告环节再将结果整理为对应成果。

### 多 Agent：规划、计算和表达，各自负责一段

task-plan Agent 负责把目标变成执行计划。它组织数据探索、检索相关资料，列出步骤、依赖和验收标准，再调度其他 Agent。遇到“先叠加还是先统计”“需要哪些评价因子”这类问题，先在规划阶段厘清，避免算到一半才发现缺数据。

data-retrieval Agent 负责摸清手头的数据。数据清单不只列文件名，还要包含坐标系、几何类型、字段和空间范围。例如，看到一个名为“土壤”的图层，仍要查询其中是否真有 pH、有机质等所需属性，不能凭文件名推断数据齐全。

gis-tool Agent 负责执行具体空间操作。缓冲、裁剪、相交、融合与属性统计等步骤，通过统一的 GIS MCP 服务调用，由内置 Python 工具、WhiteboxTools、GDAL 或 QGIS 执行。它通过统一的工具接口完成空间计算，按步骤核对参数与结果，并将执行信息留给后续复核和成果整理。

gis-data-visualisation Agent 与 report Agent 负责把结果交出去。前者组织地图图层、符号与配色，调用基于 PyQGIS 的制图服务；后者读取计划、执行日志和实际结果，编写过程报告或评价报告。报告以 Markdown 格式输出至 `03_Result`；其中的统计结论以实际工具输出为依据。

角色分开后，工具执行 Agent 可以专注于参数和结果，报告 Agent 则围绕已产生的证据组织文字。专业判断、计算记录和成果表达不再挤在同一个长对话里反复传递。

### Workflow：每一步做什么，也写清怎样才算做完

项目内置了标准分析、数据画像、单步执行、可视化报告和调试等 Workflow 模板。复杂分析按“检查工作空间—数据画像—执行空间操作—制作成果—验证目标”的顺序推进，规划 Agent 根据任务计划生成执行脚本，保存到工作区。简单任务直接委派 GIS 执行 Agent，中等任务按计划逐步委派，复杂任务再使用 Workflow。

例如，分析道路周边的耕地分布，需要先确认道路和地类数据的范围与坐标系，再生成指定距离的缓冲区，与耕地图斑叠加，统计面积，最后出图。后一步依赖前一步的真实输出，距离、面积单位与统计范围也要在计划中说清楚。

工作流从三个层次检查任务：

- **输入与参数能不能执行？** 数据画像核对已有数据，参数检查再确认必填项、类型和输入路径，减少因参数缺失造成的无效调用。
- **单步结果是否合理？** 执行后检查输出数据的属性、几何类型、坐标系与空间范围；对需要观察空间覆盖的任务，再结合图像和数据核查异常。
- **整项任务是否达到原定目标？** 最后对照计划中的验收标准检查成果是否存在、分析范围是否正确、交付内容是否齐全，并记录验证证据。

工具返回成功后，结果还要经过核查才能进入后续步骤。标准工作流提供了失败修复和续跑路径，由规划 Agent 根据记录处理失败步骤。

### Skill：把业务方法保存下来，下次接着用

GIS 工具知道如何做缓冲和叠加，却不会自动决定一份耕地评价需要哪些指标、报告应该交代什么。Skill 用于保存这些分析和表达方法：任务规划、参数确认、工具执行、错误修复、制图、过程报告与结论报告，都有对应的引导内容。

在规划阶段，LinkTool 还通过知识检索查找相关规范与相近案例，为方法选择提供依据。面对评价任务，规划 Agent 结合检索资料核对适用区域、评价单元与指标要求，再安排相应计算，让专业方法落实到具体步骤中。

这些方法按任务阶段加载。做数据探索时关注字段与范围，写报告时再组织章节和图表，避免把全部规则一次塞进上下文。团队积累的新业务流程，也能沿着 Agent、Skill 和 Workflow 的结构继续补充。

### Hook：把过程约束落到调用前后

Hook 在工具调用前后自动触发检查脚本，落实路径保护、参数检查与日志记录等过程要求。

执行前，路径保护和命令守卫检查操作范围；GIS 调用还经过参数校验、备份处理与输出路径检查。工作目录按 `01_DataBackup`、`02_WorkSpace`、`03_Result` 分区，分别放原始数据、中间数据和最终成果，原始数据区按只读规则保护。

执行后，日志脚本记录工具名、参数、输入输出路径与时间等信息，结果校验脚本再检查数据并向 Agent 反馈异常。对话历史压缩后，另有 Hook 从日志构建操作摘要，帮助后续分析接上已有进度。这些记录便于排查和复核；重现分析时仍需保留对应的数据与运行环境。

以耕地评价为例，报告里一张“各等级面积统计表”，应能对应到结果图层和统计操作；如果发现某乡镇面积异常，就能沿着路径回查筛选、叠加和计算步骤。过程报告因此有了可核对的依据，而不只是对结果的文字说明。

### MCP：接到真实工具，再组织地图和报告

GIS MCP 服务通过内置 Python 工具、WhiteboxTools、GDAL 和 QGIS 承接空间处理与数据查询，PyQGIS 制图服务负责符号系统和专题图输出，PDF 阅读、网络检索及知识库服务辅助理解资料。插件把这些服务接到同一套调度流程中，用户可以围绕业务目标持续提出需求。

插件使用开源 GIS 工具链，部署时需要准备 Python、QGIS、GDAL 和 WhiteboxTools 等运行依赖，并按需配置检索、地图等外部服务。

## 03 实测：用江屯镇数据完成一次耕地质量评价

这次，我们把广宁县江屯镇的土地利用、土壤和地形数据交给 LinkTool-ClaudeCode，要求它依据广东省三普耕地质量评价技术细则，完成评价计算，并交付地图、统计表、报告和数据库。测试使用 **DeepSeek**，从任务处理到成果生成共耗时 **4 小时 37 分钟**，而在正常情况下，这通常要花费3-4天。

### 先看数据：评价依据和空间资料一起交给插件

输入资料放在 `01_DataBackup/三普耕地质量`。其中，`江屯镇数据.gdb` 保存空间数据，Excel 补充土种属性，技术细则提供评价方法。具体内容如下。

- **`DLTB`**：土地利用图斑。从地类编码 `0101`、`0102`、`0103` 提取水田、水浇地和旱地，作为评价底图；河流、沟渠等地类也用于水资源与排水条件的距离分析。
- **`XZQ`、`XZQJX`**：行政区面与行政区界线，用于理解研究区范围和地图表达。
- **`高标`**：高标准农田图斑，与河流、沟渠资料共同辅助判断水资源和排水条件。
- **`三普土壤图`**：土壤类型资料，通过空间连接为评价单元补充土类、土属、土种等属性，再以土种关联厚度和质地构型对照表。
- **`母岩数据`**：土壤母岩背景资料；本次 12 项指标计算未将其单独作为评价因子。
- **六类土壤属性栅格**：`_441223广宁县_pH_tif` 对应酸碱度；`_441223广宁县_有机质_tif` 对应有机质含量；`_441223广宁县_有效磷_tif`、`_441223广宁县_速效钾_tif` 对应养分含量；`_441223广宁县_土壤容重平均值_tif` 对应土壤容重；`_441223广宁县_耕作层厚度_tif` 对应耕作层厚度。按评价单元提取栅格统计值后，这些数据进入指标计算。
- **四类颗粒含量栅格**：`_441223广宁县_0_002mm以下颗粒含量_tif`、`_441223广宁县_0_02_0_002mm颗粒含量_tif`、`_441223广宁县_0_2_0_02mm颗粒含量_tif`、`_441223广宁县_2_0_2mm颗粒含量_tif`，分别记录小于 0.002 mm、0.002—0.02 mm、0.02—0.2 mm、0.2—2 mm 粒径组分的含量，用于判定耕层质地。
- **`DEM`**：数字高程模型，提供地形分析基础。本次结合相对高程与坡度推导地形部位。
- **《广宁县评价单元土种与有效厚度质地构型对照0712-1.xlsx》**：按土种补充有效土层厚度和质地构型，填补仅靠现有栅格无法直接获得的指标。
- **《广东省第三次全国土壤普查县级耕地质量等级评价技术细则（试行稿）》及识别文本**：提供评价分区、指标权重、隶属度函数、等级划分和成果组织要求。

### 从一句要求到可执行的评价计划

任务从“依据技术细则，对江屯镇数据进行耕地质量分析”开始。task-plan 读取识别后的技术细则，检查数据库与补充资料，把目标拆成评价单元构建、指标赋值、标准化与等级计算、成果编制几个阶段。

这一步也把需要业务判断的条件摆到了执行前：有效土层厚度与质地构型采用新增 Excel 对照表；水资源、排水条件利用高标准农田和河流、沟渠的距离推导；地形部位采用相对地形位置与坡度方法。粮食产能资料缺失，本次保留对应字段并留空。用户确认这些处理口径后，规划结果写入任务计划。

### 运行中的约束、检查与调整

实际执行中也出现了中断。写入任务计划时，Hook 发现目标路径不在当前识别的工作空间范围内，拦截了 Bash 命令。这次提示暴露的是启动目录与输出目录之间的不一致：插件把数据所在子目录识别成了工作空间，计划却准备写入项目级 `02_WorkSpace`。路径边界在执行前给出了明确反馈，工作空间设置也因此成为排查的一部分。

![Hook 对输出路径的检查](https://raw.githubusercontent.com/Link-Tool/LinkToolImg/%E6%8F%92%E4%BB%B6%E7%B3%BB%E5%88%97/published/cc-plugin/20261017/hook%E6%8B%A6%E6%88%AA.png)

## 04 一起把更多 GIS 场景带进来

如果你已经准备好 Claude Code 环境和插件所需的开源 GIS 运行依赖，可以从一个范围清楚的小任务开始：查询一类地块、统计道路邻近区域，或把已有分析结果整理成专题图和过程报告。先把输入数据、分析口径与交付要求说清楚，再逐步尝试多因子评价等复杂流程。

插件支持按目录加载。按仓库安装指南准备依赖后，在自己的项目目录中放好 `01_DataBackup`、`02_WorkSpace` 和 `03_Result` 三个文件夹，将原始资料放入备份区，再通过 `claude --plugin-dir <插件目录>` 启动并提出需求。具体安装方式与依赖以仓库说明为准。

开源项目需要业务现场的反馈。如果某类数据识别不准，记录数据结构和报错；如果一套方法已经在项目中反复使用，可以把步骤、参数依据和验收条件整理出来。代码修复、文档补充、Skill 和 Workflow 改进，都能让下一位使用者少走一段弯路。分享案例时，请使用可公开或已脱敏的数据。

**源码、安装指南与贡献入口：[LinkTool GitHub 仓库](https://github.com/Link-Tool/LinkTool-ClaudeCode)。**
